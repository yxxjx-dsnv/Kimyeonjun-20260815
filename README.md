**정확한 상품명을 몰라도, 기억나는 특징의 서술만으로 상품을 찾아주는 대화형 탐색 에이전트.**

쇼포트의 신규 카테고리 에이전트를 제안하는 형태로, **실제 쇼포트 앱 화면을 기준으로 UI를 재현**해 구현한 레브잇 PMF 직무 과제 프로토타입입니다.

# 구현에 대한 설명

## 1. 어떤 문제를 풀었나 — 과제 1과의 연결

과제 1에서 정의한 문제는 하나의 구매 여정에 이어진 두 가지입니다.

1. **탐색** — 명품 상품명은 외국어 고유명사 조합(*크리스찬디올 SADDLE 플랩 카드 지갑 S5611CTZQ M928*)인데, 사람 머릿속에 상품은 **이름이 아니라 특징의 묘사**로 저장됩니다. 키워드 검색창은 이 묘사를 받아주지 못합니다.
2. **결정** — 고가 상품이라 "이 가격에 사도 되나"라는 확신이 없으면 결제를 미루고, 미뤄진 구매 의도는 대부분 돌아오지 않습니다.

이 프로토타입은 쇼포트가 지향하는 **메타 커머스** 관점을 따릅니다. 특정 판매처의 이해관계에 묶이지 않고 5개 쇼핑몰을 함께 수집해, 지금 이 가격이 같은 종류 안에서 어디쯤인지를 그대로 보여줍니다. 명품(과제 1의 비치헤드)에서 시작해 쇼포트의 실제 커버리지인 패션·뷰티·생활·가전까지 같은 구조로 확장했습니다.

UI는 실제 쇼포트 앱을 설치해 화면 단위로 확인하고 그 문법(홈 히어로 입력 카드, 2×2 질문 선택지, 말풍선 없는 에이전트 발화, 질문 카드와 선택지)을 재현했습니다. 별도 서비스가 아니라 **쇼포트 인앱 신규 기능 제안**으로 읽히게 하기 위해서입니다. 화면과 README 모두에 실제 쇼포트 서비스가 아닌 과제 프로토타입임을 고지했습니다.

## 2. 설계 입력을 자사 앱 리뷰에서 가져왔습니다

기능을 정하기 전에 쇼포트 앱스토어 1점 리뷰를 읽고, 불만 한 줄마다 대응하는 구현 규칙을 정했습니다. 이 프로토타입의 대화 정책은 대부분 여기서 나왔습니다.

| 리뷰가 지적한 것 | 대응 |
|---|---|
| "질문도 너무 많이 물어봐서 지치고" | 되묻기를 **대화당 1회**로 제한, 2턴째부터 코드가 차단 |
| "대답한거 싸그리 무시하고 지 맘대로 결과 보여줍니다" | 답한 조건(브랜드·예산·갈래)을 **서버가 필터로 강제** |
| "요구한거 제대로 반영도 못하고" | 갈래가 다르면 후보를 비우고 못 찾았다고 말함 |
| "그렇다고 빠른것도 아니고" | 1단계 검색으로 요청당 24k → 2~7k 토큰, 진행 단계를 화면에 노출 |
| "쇼핑 특화된 기능도 안보여서 차라리 지피티한테" | GPT가 못 하는 것 — **실제 매물·실제 가격·판매처별 비교** |

마지막 줄이 *"바이브코딩으로 하루만에 만든 앱같아요"*였습니다. 그 반대를 목표로 삼았습니다.

## 3. 강조하고 싶은 설계 판단

**(1) 2단계 검색 — 싼 필터로 넓게 거르고, 비싼 모델로 정밀하게 재순위.**
948건 전체를 매 요청 프롬프트에 넣자 OpenAI 분당 토큰 한도(429)에 걸리는 것을 E2E 테스트에서 실측했습니다. 브랜드·갈래·예산으로 먼저 100건 안팎까지 좁히고, AI는 좁혀진 목록에서 고르게 했습니다. 요청당 **24k → 2~7k 토큰**으로 줄었고 상품 수가 늘어도 구조가 버팁니다. 정보검색에서 cascade ranking이라 부르는 구조입니다.

**(2) 미니 카탈로그 파이프라인 — 흩어진 상품 정보를 비교 가능한 구조로.**
5개 소스의 상품명 형식은 전부 다릅니다(품번 포함 정식명 / [브랜드] 접두 / 서술형). 크롤러가 속성을 추출·구조화하고(브랜드+축약형 별칭, 종류 26종, 모델 라인 키워드, 리뷰 평점), `브랜드|종류|모델` 그룹으로 묶어 **소스가 달라도 같은 상품끼리** 비교되게 했습니다. 서로 다른 판매처가 한 그룹에 묶인 비교 그룹 89개 — 판매처별 가격 비교가 실데이터로 동작합니다.

**(3) 정적 카탈로그 + 실시간 검색의 병합, 그리고 동의를 받는 확장.**
948건은 시세 계산의 기준선이고, 카탈로그에 없는 상품은 질의 시점에 실시간 검색으로 보완합니다. 그래도 못 찾으면 **없다고 먼저 말한 뒤** "웹 검색까지 넓혀서 찾아드릴까요?"를 제시하고, 고객이 누른 경우에만 느린 소스까지 포함해 다시 찾습니다. 조용히 엉뚱한 상품을 채우지 않기 위해서입니다.

**(4) 대화 정책을 프롬프트가 아니라 코드로 강제 — 5중 가드.**
대화형 AI 제품의 실패는 대부분 "모델이 틀렸다"가 아니라 "틀린 것이 그대로 사용자에게 나갔다"입니다. 모델 출력과 화면 사이에 검증 계층을 두었습니다.

| 가드 | 막는 것 |
|---|---|
| 브랜드 | 언급한 브랜드 외 상품 (단, "비슷한 거/대체품"이면 예외) |
| 갈래 | 요청한 물건의 갈래가 다른 후보 — 슬리퍼를 물었는데 지갑이 나오는 경우 |
| 예산 | 말한 범위를 벗어난 가격 |
| 모순 | 상품이 있는데 "없다", 0건인데 "추천드릴게요" — 양방향 |
| id 조인 | AI가 지어낸 상품 id는 카탈로그 조인에서 걸러져 화면에 못 올라옴 |

되묻기 선택지는 **탭 가능한 칩**으로 제공해 40~50대 사용자의 타이핑 부담을 줄였습니다.

**(5) 숫자의 정직함 — 근거가 약하면 숫자를 만들지 않습니다.**
- AI는 가격을 언급할 수 없습니다(환각 위험). 가격은 전부 서버가 크롤링 데이터로 계산합니다.
- 비교군 3건 미만이면 시세를 만들지 않습니다.
- 최고/최저 편차 **1.5배 초과** 그룹은 "시세 대비 N%" 대신 "N건 중 M번째로 저렴"이라는 반박 불가능한 사실만 보여줍니다.
- 그 결과 948건 중 **% 주장이 성립하는 것은 73건(7.7%)뿐**입니다. **이 숫자가 작다는 것이 이 설계의 요점입니다.**

**(6) 검증을 코드로 남겼습니다** — `tests/`, 심사 시 직접 실행 가능합니다.

| 명령 | 내용 |
|---|---|
| `npm test` | 순수 로직 self-check 2종 + SSR 렌더 22항목 + **검색 회귀 8항목** (외부 의존 없음) |
| `npm run stats` | 카탈로그·시세 통계. **이 README의 수치는 전부 이 명령의 출력입니다** |
| `npm run test:api` | OpenAI 실호출 E2E. 과거 실패 사례가 회귀 테스트로 고정 (`.env.local` 필요) |
| `npm run test:browser` | Playwright 실브라우저 플로우 |
| `node tests/shots.mjs` | 발표자료용 스크린샷 6장 자동 촬영 |

## 4. 설계 근거로 참고한 것

기능을 정할 때 감이 아니라 이미 측정된 것을 먼저 찾았습니다.

| 설계 결정 | 근거 |
|---|---|
| 속성·용도 검색을 노린 이유 | 이커머스 검색 결함률: 정확한 상품명 12% vs **속성 39%·용도 43%** (Baymard Institute, 170+ 사이트 벤치마크 — 논문 아님) |
| 되묻기로 속성을 구조화하는 이유 | 이름 대신 속성으로 찾게 하자 완전 검색 성공률 **21% → 77%** (Yee et al., ACM CHI 2003, n=32) |
| 사용자가 모호하게 말한다는 전제 | 이름 모르는 물건을 찾는 문장의 **35.4%**가 불확실 표현 (Arguello et al., ACM CHIIR 2021) |
| 2단계 검색 구조 | cascade ranking (Wang, Lin & Metzler, SIGIR 2011 / Liu et al., KDD 2017 — 타오바오 운영 배포) |
| 상품 id만 출력하게 강제 | constrained decoding (De Cao et al., ICLR 2021 / OpenAI Structured Outputs) |
| 후보 3개 제한 | 선택 과부하 (Iyengar & Lepper, JPSP 2000 — 잼 24종→6종, **부스 방문자** 구매율 3%→30%) |
| 시세 분포 제시 | 준거가격·거래효용 (Thaler, Marketing Science 1985) |
| 타깃을 40~50대 여성으로 좁힌 이유 | 40~50대 여성 200명 중 **49%가 큐레이션 서비스를 원하지만 이용 경험은 0%** (이정은·김동은, 한국의류산업학회지 2022) / 온라인 쇼핑 최다 지출은 40대인데 전문몰 이용은 20대 48% → 40대 31% → 50대 22% (CJ메조미디어 2026, n=1,000) |

**인용의 한계를 스스로 적어둡니다.** 반박당할 수 있는 지점을 숨기지 않는 편이 안전하다고 판단했습니다.

- 선택 과부하는 **Scheibehenne et al.(2010) 메타분석에서 재현에 실패**했습니다. 다만 Chernev et al.(2015)은 *과제 난이도·선호 불확실성*을 조절변수로 넣으면 유의하다고 보고하며, 모델명과 시세를 모르는 명품 탐색이 그 조건에 해당한다고 판단했습니다.
- **후보 "3개"는 문헌이 검증한 수가 아닙니다.** 문헌의 소집합 표준은 6입니다. 3은 채팅 UI에서 스크롤 없이 한 화면에 들어가는 수라는 인터페이스 제약에서 나왔고, 3 vs 6은 A/B 테스트 1순위 항목입니다.
- Urbany et al.(1988)은 **과장된 준거가격도 단기 효과가 있다**고 보고합니다. 그럼에도 % 주장을 포기한 것은 효과가 없어서가 아니라, 재구매 기반 서비스에서 한 번의 거짓이 LTV를 깎기 때문입니다.
- constrained decoding은 공짜가 아닙니다. Tam et al.(EMNLP 2024)은 엄격한 형식 강제가 추론 성능을 떨어뜨림을 보고합니다. 환각 0을 위해 추론 여유를 일부 포기한 선택입니다.
- Baymard는 **상업 UX 리서치 기관**이며 논문이 아닙니다. Yee et al.(2003)은 이미지 컬렉션 연구로, 커머스 전이는 저희 가정입니다.

출처를 답할 수 없는 수치(벤더 블로그발 "검색 실패 시 N% 이탈" 류)는 의도적으로 전부 배제했습니다.

## 5. 겪은 어려움과 해결

**① 첫 크롤링 타깃 — 200 OK가 성공이 아니었다**

처음 타깃이던 중고명품 마켓은 봇 차단 없이 200을 주고 상품 100건이 서버렌더링되어 있어 파싱까지 마쳤습니다. 그런데 우리가 사용한 요청 방식에서는 **"디올 지갑"과 "구찌 가방"의 결과가 완전히 동일**했고, 명품이 아닌 상품까지 섞여 있었습니다. 검색 결과가 아니라 고정 목록을 받고 있었던 것입니다.

> **배운 것**: 응답 코드와 그럴듯한 HTML은 크롤링 성공의 근거가 못 됩니다. **입력(검색어)을 바꿨을 때 출력이 실제로 달라지는지**까지 확인해야 검증이 끝납니다.

**② 크롤링 소스 확장 — 20곳을 실측해서 5곳이 남았다**

위 교훈을 기준 삼아, 파서를 쓰기 전에 curl로 먼저 실측했습니다.

| 결과 | 소스 |
|---|---|
| **채택 (5)** | **다나와**(판매처별 최저가·SSR) · **컬리**(뷰티/생활) · **29CM**(패션) · **무신사**(패션, `caller=SEARCH` 파라미터 필요) · **KREAM**(리셀 시세) |
| 검색어 무반응 | 필웨이 (200이지만 결과가 질의와 무관) |
| 403 차단 | 네이버쇼핑, eBay, SSG, G마켓, 올리브영 |
| SPA/오류 | 트렌비, 발란, 머스트잇, 에누리, W컨셉, 헬로마켓, 중고나라, 11번가 |

**KREAM은 일반 요청이 WAF에 막혀 한 번 탈락시켰다가, 실제 브라우저(Playwright)로 우회해 되살렸습니다**(48건). 스니커즈·한정판은 리셀 시세가 곧 실거래가라 "이 가격이 적정한가"에 가장 직접적인 근거가 되는 소스여서, 막혔다고 버리는 대신 방법을 바꿨습니다.

**③~⑨ 실사용·자동화 테스트에서 잡은 결함**

3. **"샤넬 가방"에 7만원짜리 빈 상자가 매칭.** 제목이 `*클래식백* 샤넬 자석 박스 … 쇼핑백`이라 텍스트상 완벽한 후보였습니다. 부속품 필터를 넣되 `박스`를 통으로 막으면 "가방 + 박스"(진짜 가방)가, `참`을 막으면 `참월렛`(480만 원)이 죽어서 **합성어 단위로만** 차단했습니다.

4. **"샤넬 검정 누빔"에 생로랑 마틀라세가 노출.** LLM이 속성 유사도만 보고 브랜드를 무시한 실사용 사례. 언급된 브랜드 외 상품을 **서버가 걸러내는 브랜드 가드**를 추가하고 회귀 테스트로 고정했습니다.

5. **전체 카탈로그 프롬프트가 분당 토큰 한도(429)에 걸림.** E2E가 잡아낸 확장성 문제 — 1단계 검색 도입으로 해결.

6. **시세 왜곡 — "72% 저렴"이 서로 다른 상품 간 비교였음.** 배포 후 자체 점검에서 발견했습니다. 원인이 두 개였습니다. (a) 편차 4배까지 한 시세로 허용해 물티슈 60매가 70매 4팩과 비교됨. (b) 짝수 개 그룹에서 중앙값 대신 '가운데 위' 값을 써서 **할인율이 구조적으로 항상 과장**됨. 편차 상한을 1.5배로 조이고 중앙값 계산을 고쳤습니다. 조치 후 최대 할인 주장이 **72% → 29%**로 내려갔고, 상위 항목이 전부 품번까지 일치하는 동일 상품이 되었습니다.

7. **"메종 키츠네 니트인데 큰 여우가 그려진거"에 9,800원짜리 무신사 기본 니트가 나옴.** 이 서비스의 존재 이유가 걸린 실패라 가장 중요하게 다뤘습니다. 원인은 한 줄이었습니다 — 질의는 공백을 지워 비교하는데(`"메종키츠네니트..."`) **브랜드명은 원문 그대로**(`"메종 키츠네"`) 비교하고 있어서, 이름에 공백이 있는 브랜드 **18개가 전부 인식 불가**였습니다(메종 키츠네·조 말론 런던·에스티 로더·바비 브라운·무신사 스탠다드·끌레드뽀 보떼 등). 브랜드가 무시되니 `니트` 카테고리 16건만 후보가 됐고, 정답인 메종 키츠네 제품은 카테고리가 **가디건**이라 후보에서 아예 빠졌습니다.
   같은 계열 문제가 둘 더 있었습니다. 인스턴트 검색도 공백을 지워 한 덩어리로 비교해 `"디올 지갑"`이 0건이었고(토큰 AND 매칭으로 교체), 카탈로그에 `숄더백`만 있고 `가방`은 없어서 `"샤넬 가방"`이 0건이었습니다(상위어 매핑 추가).

8. **AI가 상품 3건을 보여주면서 동시에 "그런 상품이 없습니다"라고 답함.** 프롬프트 규칙이 서로 충돌했고(한 규칙은 최소 6문장, 다른 규칙은 2~3문장), 후보 없을 때의 안내 문구를 기존 답변에 **덧붙여** 모순이 완성됐습니다. 규칙을 축약하고 문구를 교체 방식으로 바꾼 뒤, 후보가 있는데 "없다"고 쓰면 **서버가 최종 차단**하도록 했습니다. 응답 길이도 128자 → 24~32자로 줄었습니다.

9. **자체 탐침 62건에서 나온 결함 7종.** 6가지 질의 유형(브랜드·서술형·대화이력·상위어/예산·없는물건·표기변형)으로 실서비스를 두들겨 재현 검증을 거쳤습니다. 대표적으로 — 정정 발화("아니 가방이었어")에서 앞턴의 갈래가 계속 이기던 문제, 액세서리(벨트·시계) 갈래가 인식 테이블에 아예 없던 문제, 영어 질의에 갈래 판정이 무력하던 문제, `'가죽'` 같은 범용어 하나로 검색 캐스케이드가 조기 종료돼 정답(보테가베네타 인트레치아토)을 **찾아놓고 버리던** 문제입니다.

## 6. 아쉬운 점 · 개선 여지

**지금 구조의 한계**

- **가격 이력이 없어 "평소보다 싸다"를 말할 수 없습니다.** 현재는 같은 시점의 상품 간 비교라, 쇼포트 본 앱의 "평소보다 N%↓"처럼 자기 자신의 이력과 비교하는 방식보다 근거가 약합니다. 주기 재수집(cron)으로 이력을 쌓는 것이 1순위 개선입니다.
- **묘사어와 상품 용어를 잇는 사전이 없습니다.** "격자 무늬"를 "체크"로, "바구니처럼 엮은"을 "인트레치아토"로 옮기지 못합니다. 브랜드가 명시되면 잘 찾지만, 순수 묘사만으로는 순위 품질이 떨어집니다.
- **매칭이 텍스트 기반이라 상품명에 없는 정보는 못 찾습니다.** "금색 D 장식" 같은 묘사는 판매자가 안 쓰면 반영되지 않습니다. 상품 이미지를 Vision 모델로 캡셔닝해 속성을 미리 생성해 두는 방향을 생각하고 있습니다.
- **1단계 검색이 규칙 기반입니다.** 브랜드·갈래 감지는 정확하지만 "결혼식 하객룩" 같은 상황형 질의는 못 좁힙니다. 임베딩 검색으로 교체하면 지금 구조(검색→LLM) 그대로 업그레이드됩니다.
- **동일 상품 판별이 거칩니다.** 소스 간 같은 모델 매칭이 키워드 규칙이라 신규 라인·비표준 표기를 놓칩니다. % 주장이 가능한 상품이 73건뿐인 이유이기도 합니다.

**검증하고 싶은 것 (과제 1의 실험 설계와 연결)**

- H1(서술형 검색이 발견율을 높이는가) — 3턴 내 발견율, 대화 시작→카드 클릭률.
- H2(가격 근거가 결제를 앞당기는가) — 가격 정보 노출/미노출 A/B로 구매 링크 클릭률 비교. **가격 비교 정보가 전환율을 얼마나 올리는지에 대한 이커머스 현장 실험은 문헌에서 찾지 못했습니다.** 문헌으로 답이 나오지 않는 지점이라 실험으로 남겨두었습니다.
- 못 찾은 묘사는 "무엇을 원했는데 없었는가"라는 수요 데이터입니다. 저장해서 소싱 우선순위로 쓸 수 있습니다.

**회고**

이번 과제에서 가장 큰 수확은 "입력을 바꿔 출력이 달라지는지 확인하기 전까지 검증이 아니다"라는 기준이었습니다. 이 기준 덕분에 소스 실측(20곳)이 빨라졌고, 같은 태도를 제품 쪽에도 적용했습니다.

특히 **배포한 뒤에 발견한 결함들이 가장 값졌습니다.** 시세 왜곡도, 응답 모순도, 공백 하나 때문에 브랜드 18개가 죽어 있던 것도 화면상으로는 정상으로 보였습니다. 숫자와 문장과 결과를 직접 대조해야 드러났고, 그중 몇 개는 이전 수정이 만든 새 결함이었습니다. **기준을 정하는 것과 그 기준이 실제로 지켜지는지 확인하는 것은 다른 일이었습니다.** 그래서 지금은 고칠 때마다 회귀 테스트를 같이 넣고, README의 수치를 `npm run stats`로 코드에서 뽑아 문서와 대조합니다.

AI 제품에서 신뢰는 모델의 선의가 아니라 구조가 만들어야 한다고 생각합니다.
