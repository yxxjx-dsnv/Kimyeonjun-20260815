# 쇼포트 명품 에이전트 (프로토타입)

**정확한 상품명을 몰라도, 기억나는 특징의 서술만으로 상품을 찾아주는 대화형 탐색 에이전트.**
찾아준 상품이 같은 종류의 다른 매물 대비 어느 위치에 있는지까지 계산해 제시합니다.
쇼포트의 신규 카테고리 에이전트를 제안하는 형태로, **실제 쇼포트 앱 화면을 기준으로 UI를 재현**해 구현한 레브잇 PMF 직무 과제 프로토타입입니다.

🔗 **배포 링크: https://luxury-agent-demo.vercel.app**

```
"디올 카드지갑인데 새들 모양에 금색 D 장식 달린 거"
                       ↓
        AI가 후보 3개 + 조건에 맞는 이유
      + 같은 그룹 4건 중 최저가 · 시세 대비 29% 저렴
```

> 이 문서의 모든 수치는 `npm run stats` 실행 결과와 일치합니다. (2026-08-16 기준)

## 로컬 실행

```bash
npm install
echo "OPENAI_API_KEY=sk-..." > .env.local

npm run crawl      # (선택) 상품 데이터 재수집 → data/products.json
npm run stats      # 카탈로그·시세 통계 출력 (이 README의 수치 검증용)
vercel dev         # http://localhost:3000 — 프론트 + /api 함께 실행
```

`vercel dev` 없이 프론트만 볼 때는 `npm run dev` (5173 → 3000으로 `/api` 프록시).

# 구현에 대한 설명

## 1. 어떤 문제를 풀었나 — 과제 1과의 연결

과제 1에서 정의한 문제는 하나의 구매 여정에 이어진 두 가지입니다.

1. **탐색**: 명품의 상품명은 외국어 고유명사 조합(*크리스찬디올 SADDLE 플랩 카드 지갑 S5611CTZQ M928*)인데, 사람 머릿속에 상품은 **이름이 아니라 특징의 묘사**로 저장된다. 키워드 검색창은 이 묘사를 받아주지 못한다.
2. **결정**: 고가 상품이라 "이 가격에 사도 되나"라는 확신이 없으면 결제를 미루고, 미뤄진 구매 의도는 대부분 돌아오지 않는다.

이 프로토타입은 쇼포트가 지향하는 **메타 커머스** 관점을 그대로 따릅니다. 특정 판매처의 이해관계에 묶이지 않고 5개 쇼핑몰을 함께 수집해, 지금 이 가격이 같은 종류 안에서 어디쯤인지를 그대로 보여줍니다. 명품(과제 1의 비치헤드)에서 시작해 쇼포트의 실제 커버리지인 패션·뷰티·생활·가전 카테고리까지 같은 구조로 확장했습니다.

UI는 실제 쇼포트 앱을 설치해 화면 단위로 확인하고 그 문법(홈 히어로 입력 카드, 2×2 질문 선택지, 말풍선 없는 에이전트 발화, 질문 카드와 선택지)을 재현했습니다 — 별도 서비스가 아니라 **쇼포트 인앱 신규 기능 제안**으로 바로 읽히게 하기 위해서입니다. 화면과 README 모두에 실제 쇼포트 서비스가 아닌 과제 프로토타입임을 고지했습니다.

## 2. 강조하고 싶은 설계 판단

**(1) 미니 카탈로그 파이프라인 — 흩어진 상품 정보를 비교 가능한 구조로.**
5개 소스의 상품명 형식은 전부 다릅니다(품번 포함 정식명 / [브랜드] 접두 / 서술형). 크롤러가 **속성을 추출·구조화**하고(브랜드+축약형 별칭, 종류 26종, 명품 모델 라인 키워드, 리뷰 평점), `브랜드|종류|모델` 그룹으로 묶어 **소스가 달라도 같은 상품끼리** 비교되게 했습니다. 서로 다른 판매처가 한 그룹에 묶인 비교 그룹 89개 — "쿠팡·11번가식 판매처별 가격 비교"가 실데이터로 동작합니다.

**(2) 정적 카탈로그 + 실시간 검색의 병합.**
948건은 시세 계산의 기준선이고, 카탈로그에 없는 상품은 질의 시점에 실시간 검색으로 보완합니다. 두 결과를 같은 그룹 규칙으로 병합해 비교 대상에 함께 넣습니다. 덕분에 "카탈로그에 없어서 못 찾는다"는 상황을 줄이면서도 가격 근거는 수집 데이터로 계산합니다.

**(3) 대화 정책 — 흔한 실패 패턴의 정반대, 프롬프트가 아니라 코드로.**
대화형 쇼핑 에이전트가 실사용에서 가장 많이 비판받는 패턴은 "질문만 계속하고 결과를 안 준다", "대답해도 무시한다"입니다. 정책을 서버 코드로 강제했습니다:

- **질문은 대화 전체에서 최대 1번.** 후보를 함께 제시한 채로만 물을 수 있고, 2턴째부터는 코드가 되묻기를 차단.
- **매 턴 후보 필수.** AI가 빈손이면 키워드 매칭(브랜드·종류·색상 점수화)이 백스톱으로 후보를 채움.
- **브랜드 가드.** 언급된 브랜드 외 상품은 코드 레벨에서 차단 (실사용 버그에서 도입 — 아래 결함 ④).
- **모순 차단.** 후보를 제시하면서 "없다"고 말하면 서버가 문구를 교체 (아래 결함 ⑦).
- 되묻기 선택지는 **탭 가능한 칩** — 40-50대 사용자의 타이핑 부담을 줄입니다.

**(4) 1단계 검색(retrieval) — 요청당 24k → 2~7k 토큰.**
전체 카탈로그를 매 요청 프롬프트에 넣자 OpenAI 분당 토큰 한도(429)에 걸리는 것을 E2E 테스트에서 실측했습니다. 대화에서 감지한 브랜드·카테고리로 카탈로그를 좁혀 보내고, 단서가 없으면 그룹별 대표 2건으로 요약해 보내는 검색 단계를 서버에 구현했습니다. 상품 수가 늘어도 버티는 구조가 됐습니다.

응답 시간은 실측 기준 **캐시 미적중 3.6~4.9초**입니다. 실시간 검색이 함께 도는 경로라 이보다 길어질 수 있어, 변형 검색 캐스케이드에 시간 상한을 두었습니다.

**(5) 숫자의 정직함 — 근거가 약하면 숫자를 만들지 않는다.**
- AI는 가격을 언급할 수 없습니다(환각 위험). 가격은 전부 서버가 크롤링 데이터로 계산합니다.
- AI가 지어낸 상품 id는 카탈로그 조인에서 걸러져 화면에 못 올라옵니다.
- 비교군 3건 미만이면 시세를 만들지 않고, **최고/최저 편차 1.5배 초과 그룹은 "시세 대비 N%" 대신 "N건 중 1번째로 저렴"이라는 반박 불가능한 사실만** 보여줍니다.
- 그 결과 948건 중 **% 주장이 성립하는 것은 73건(7.7%)뿐**입니다. 이 숫자가 작다는 것이 이 설계의 요점입니다.

**(6) 검증을 코드로 남겼습니다.** (`tests/` — 심사 시 직접 실행 가능)
- `npm test` — 순수 로직 self-check 2종 + SSR 렌더 검증 22항목 (외부 의존 없음)
- `npm run stats` — 카탈로그·시세 통계 출력. **이 README의 수치는 전부 이 명령의 출력입니다.**
- `npm run test:api` — OpenAI 실호출 E2E 시나리오. 과거 실패 사례들("샤넬백 빈손 응답", "생로랑 혼입", "빈 상자 매칭")이 회귀 테스트로 고정되어 있습니다. (.env.local 필요)
- `npm run test:browser` — Playwright 실브라우저 플로우. playwright는 별도 설치(`npm i -D playwright && npx playwright install chromium`), `vercel dev` 기동 후 실행합니다.

## 3. 겪은 어려움과 해결

**① 첫 크롤링 타깃 — 200 OK가 성공이 아니었다**

처음 타깃이던 중고명품 마켓은 봇 차단 없이 200을 주고 상품 100건이 서버렌더링되어 있어 파싱까지 마쳤습니다. 그런데 우리가 사용한 요청 방식에서는 **"디올 지갑"과 "구찌 가방"의 결과가 완전히 동일**했고, 명품이 아닌 상품까지 섞여 있었습니다. 검색 결과가 아니라 고정 목록을 받고 있었던 것입니다.

> **배운 것**: 응답 코드와 그럴듯한 HTML은 크롤링 성공의 근거가 못 됩니다. **입력(검색어)을 바꿨을 때 출력이 실제로 달라지는지**까지 확인해야 검증이 끝납니다.

**② 크롤링 소스 확장 — 20곳을 실측해서 5곳이 남았다**

위 교훈을 기준 삼아, 파서를 쓰기 전에 curl로 먼저 실측했습니다.

| 결과 | 소스 |
|---|---|
| **채택 (5)** | **다나와**(판매처별 최저가·SSR) · **컬리**(뷰티/생활·검색 API) · **29CM**(패션·검색 API) · **무신사**(패션·`caller=SEARCH` 파라미터 필요) · **KREAM**(리셀 시세·WAF 우회 수집) |
| 검색어 무반응 | 필웨이 (200이지만 결과가 질의와 무관) |
| 403 차단 | 네이버쇼핑, eBay, SSG, G마켓, 올리브영 |
| SPA/오류 | 트렌비, 발란, 머스트잇, 에누리, W컨셉, 헬로마켓, 중고나라, 11번가 |

**KREAM은 일반 요청이 WAF에 막혀 실제 브라우저(Playwright)로 우회 수집**했습니다(48건). 스니커즈·한정판은 리셀 시세가 곧 실거래가라 "지금 가격이 적정한가"에 가장 직접적인 근거가 되는 소스였기 때문에, 막혔다고 버리지 않고 방법을 바꿨습니다.

**③~⑧ 실사용·자동화 테스트에서 잡은 결함**

3. **"샤넬 가방"에 7만원짜리 빈 상자가 매칭.** 제목이 `*클래식백* 샤넬 자석 박스 … 쇼핑백`이라 텍스트상 완벽한 후보였습니다. 부속품 필터를 넣되 `박스`를 통으로 막으면 "가방 + 박스"(진짜 가방)가, `참`을 막으면 `참월렛`(480만 원)이 죽어서 **합성어 단위로만** 차단했습니다.
4. **"샤넬 검정 누빔"에 생로랑 마틀라세가 노출.** LLM이 속성 유사도만 보고 브랜드를 무시한 실사용 스크린샷 사례. 언급된 브랜드 외 상품을 **서버가 걸러내는 브랜드 가드**를 추가하고 회귀 테스트로 고정했습니다.
5. **전체 카탈로그 프롬프트가 분당 토큰 한도(429)에 걸림.** E2E가 잡아낸 확장성 문제 — 1단계 검색 도입으로 해결 (위 설계 판단 4).
6. **시세 왜곡 — "72% 저렴"이 서로 다른 상품 간 비교였음.** 배포 후 자체 점검에서 발견. 원인이 두 개였습니다. (a) 편차 4배까지 한 시세로 허용해 물티슈 60매가 70매 4팩과 비교됨. (b) 짝수 개 그룹에서 중앙값 대신 '가운데 위' 값을 써서 **할인율이 항상 과장**됨. 편차 상한을 1.5배로 조이고 중앙값 계산을 고쳤습니다. 조치 후 최대 할인 주장이 **72% → 29%**로 내려갔고, 상위 항목이 전부 품번까지 일치하는 동일 상품이 되었습니다.
7. **"메종 키츠네 니트인데 큰 여우가 가운데 그려진거"에 9,800원짜리 무신사 기본 니트가 나옴.** 이 서비스의 존재 이유가 걸린 실패라 가장 중요하게 다뤘습니다. 원인은 한 줄이었습니다 — 질의는 공백을 지워 비교하는데(`"메종키츠네니트..."`) **브랜드명은 원문 그대로**(`"메종 키츠네"`) 비교하고 있어서, 이름에 공백이 있는 브랜드 **18개가 전부 인식 불가**였습니다(메종 키츠네·조 말론 런던·에스티 로더·바비 브라운·무신사 스탠다드·끌레드뽀 보떼…). 브랜드가 무시되니 `니트` 카테고리 16건만 후보가 됐고, 정답인 메종 키츠네 제품은 카테고리가 **가디건**이라 후보에서 아예 빠졌습니다.
   같은 계열의 문제가 두 개 더 있었습니다. (a) 인스턴트 검색도 공백을 지워 한 덩어리로 비교해 `"디올 지갑"`이 0건이었고(토큰 AND 매칭으로 교체), (b) 카탈로그에 `숄더백`만 있고 `가방`은 없어서 `"샤넬 가방"`이 0건이었습니다(상위어 매핑 추가).
   조치 후: *메종 키츠네 니트인데 큰 여우가 가운데 그려진거* → **베이비 폭스 패치 레귤러 가디건**, *샤넬 가방인데 검정 누빔에 금색 체인* → **샤넬 클래식 플랩 백 캐비어 금장**. `tests/search.test.mjs`로 회귀 고정했습니다(공백 브랜드 18개 전수 검사 포함).

8. **AI가 상품 3건을 보여주면서 동시에 "그런 상품이 없습니다"라고 답함.** 프롬프트 규칙이 서로 충돌했고(한 규칙은 최소 6문장, 다른 규칙은 2~3문장), 후보 없을 때의 안내 문구를 기존 답변에 **덧붙여** 모순이 완성됐습니다. 규칙을 축약하고 문구를 교체 방식으로 바꾼 뒤, 후보가 있는데 "없다"고 쓰면 **서버가 최종 차단**하도록 했습니다. 응답 길이도 128자 → 24~32자로 줄었습니다.

## 4. 아쉬운 점 · 개선 여지

**지금 구조의 한계**

- **가격 이력이 없어 "평소보다 싸다"를 말할 수 없습니다.** 현재는 같은 시점의 상품 간 비교라, 쇼포트 본 앱의 "평소보다 N%↓"처럼 자기 자신의 이력과 비교하는 방식보다 근거가 약합니다. → 주기 재수집(cron)으로 이력을 쌓는 것이 1순위 개선입니다.
- **매칭이 텍스트 기반이라 상품명에 없는 정보는 못 찾습니다.** "금색 D 장식", "물결 모양 뚜껑" 같은 묘사는 판매자가 안 쓰면 반영되지 않습니다. → 상품 이미지를 Vision 모델로 캡셔닝해 색·형태·장식 속성을 카탈로그에 미리 **생성**해 두는 방향.
- **1단계 검색이 규칙 기반입니다.** 브랜드·카테고리 감지는 정확하지만 "결혼식 하객룩" 같은 상황형 질의는 못 좁힙니다. → 임베딩 검색으로 교체하면 지금 구조(검색→LLM) 그대로 업그레이드됩니다.
- **동일 상품 판별이 거칩니다.** 소스 간 같은 모델 매칭이 키워드 규칙이라 신규 라인·비표준 표기를 놓칩니다. 이 때문에 % 주장이 가능한 상품이 73건뿐입니다. → 품번 정규화 + 임베딩 클러스터링.

**검증하고 싶은 것 (과제 1의 실험 설계와 연결)**

- H1(서술형 검색이 발견율을 높이는가): 3턴 내 발견율, 대화 시작→카드 클릭률.
- H2(가격 근거가 결제를 앞당기는가): 가격 정보 노출/미노출 A/B로 구매 링크 클릭률 비교.
- 못 찾은 묘사는 "무엇을 원했는데 없었는가"라는 수요 데이터입니다 — 저장해서 소싱 우선순위로 쓸 수 있습니다.

**회고**: 이번 과제에서 가장 큰 수확은 "입력을 바꿔 출력이 달라지는지 확인하기 전까지 검증이 아니다"라는 기준이었습니다. 이 기준 덕분에 소스 실측(20곳)이 빨라졌고, 같은 태도를 제품 쪽에도 적용했습니다. 특히 **배포한 뒤에 발견한 결함 2건(시세 왜곡·응답 모순)이 가장 값졌습니다.** 둘 다 화면상으로는 정상으로 보였고, 자체 점검에서 숫자와 문장을 직접 대조해야 드러났기 때문입니다. AI 제품에서 신뢰는 모델의 선의가 아니라 구조가 만들어야 한다고 생각합니다.
