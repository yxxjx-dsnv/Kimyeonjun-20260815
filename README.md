# 그거 있잖아

**정확한 상품명을 몰라도, 기억나는 대로 말하면 찾아주는 AI 쇼핑 비서.**
찾아준 매물이 새상품·중고 시세 대비 얼마나 싼지까지 계산해 드립니다.

🔗 **배포 링크: https://geugeo-itjana.vercel.app**

```
"샤넬백인데 검정색 캐비어 가죽에 금장 로고 있는 거"
                       ↓
  AI가 후보 3개 + 왜 이게 맞는지 근거
+ 새상품 최저가 1,188,990원 → 이 중고 매물 620,000원 = 지금 사면 절약 568,990원
```

## 로컬 실행

```bash
npm install
echo "OPENAI_API_KEY=sk-..." > .env.local

npm run crawl      # (선택) 매물 데이터 재수집 → data/products.json
vercel dev         # http://localhost:3000 — 프론트 + /api 함께 실행
```

`vercel dev` 없이 프론트만 볼 때는 `npm run dev` (5173 → 3000으로 `/api` 프록시).

## 구조

```
crawler/crawl.js   번개장터(중고 매물) + 다나와(새상품 가격비교) 수집 — 15개 브랜드
data/products.json 크롤링 결과 473건 (중고 293 / 새상품 180)
api/_intel.js      가격 인텔리전스 공용 모듈 (시세 분포 + 새상품 대비 절약)
api/chat.js        POST — ChatGPT 상품 매칭 + 대화 정책 + 매칭 백스톱
api/catalog.js     GET — 둘러보기/찜 탭용 카탈로그 서빙
src/App.jsx        앱 셸 (AI 찾기 / 둘러보기 / 찜 3탭) + 절약 계산서 UI
```

| 호스팅 | Vercel |

# 구현에 대한 설명

## 1. 어떤 문제를 풀었나 — 과제 1과의 연결

과제 1에서 정의한 문제는 하나의 구매 여정에 이어진 두 가지입니다.

1. **탐색**: 명품의 상품명은 외국어 고유명사 조합(*디올 새들 로터스 월렛 오블리크*)인데, 사람 머릿속에 상품은 **이름이 아니라 특징의 묘사**로 저장된다. 키워드 검색창은 이 묘사를 받아주지 못한다.
2. **결정**: 고가 상품이라 "이 가격에 사도 되나"라는 확신이 없으면 결제를 미루고, 미뤄진 구매 의도는 대부분 돌아오지 않는다.

이 MVP는 쇼포트가 지향하는 **메타 커머스** 관점을 명품 카테고리에 적용한 것이기도 합니다. 특정 판매처의 이해관계에 묶이지 않고 — 중고 마켓(번개장터)과 새상품 가격비교(다나와)를 함께 수집해, 고객에게 지금 가장 합리적인 선택지가 무엇인지(중고가 얼마나 절약되는지, 오히려 새상품이 더 싼 건 아닌지)를 그대로 보여줍니다.

## 2. 강조하고 싶은 설계 판단

**(1) 미니 카탈로그 파이프라인 — 흩어진 상품 정보를 비교 가능한 구조로.**
서로 다른 두 소스(중고 C2C 매물 / 새상품 가격비교)의 상품명은 형식이 완전히 다릅니다. 크롤러가 상품명·판매자 태그에서 **속성을 추출**하고(브랜드 15종 + 축약형 별칭, 종류 8종, 모델 라인 60여 개 키워드, 새상품/중고, 검수 가능 여부), `브랜드|종류|모델` 그룹으로 묶어 소스가 달라도 같은 상품끼리 비교되게 했습니다. AI 추천의 근거 설명, 시세 계산, 새상품 대비 절약이 전부 이 구조 위에서 동작합니다.

**(2) '절약 계산서' — 가격 확신을 %가 아니라 원화로.**
새상품 최저가(다나와 집계) → 이 중고 매물 가격 → **"지금 사면 절약 568,990원"**. 구매를 미루게 만드는 질문("이 가격에 사도 되나")에 대한 답을 계산서 형태로 줍니다. 반대 방향도 숨기지 않습니다 — 중고 매물이 새상품보다 비싸면 절약액 대신 **"새상품이 더 저렴해요 → 새상품 보기"** 링크를 보여줍니다. 판매처 이해관계가 없기에 가능한 정직함이고, 이 정직함이 곧 신뢰(재방문)라고 판단했습니다.

**(3) 대화 정책 — 흔한 실패 패턴의 정반대.**
대화형 쇼핑 에이전트가 실사용에서 가장 많이 비판받는 패턴은 "질문만 계속하고 결과를 안 준다", "대답해도 무시한다"입니다. 정책으로 뒤집었습니다:

- **질문은 대화 전체에서 최대 1번.** 그마저도 후보를 함께 제시한 채로만 물을 수 있고, 2턴째부터는 프롬프트가 아니라 **코드가** 되묻기를 차단합니다.
- **매 턴 후보 필수.** 언급된 브랜드가 카탈로그에 있는 한 빈손 응답은 금지. AI가 후보를 못 고르면 서버의 키워드 매칭(브랜드+종류+색상 점수화)이 백스톱으로 후보를 채웁니다.
- **답변 인용.** reply 첫 문장은 고객이 말한 특징을 그대로 인용하며 시작하고("말씀하신 '베이지에 남색 무늬'는…"), 판매글에 없는 특징은 "확인 필요"라고 솔직히 말합니다.
- 되묻기 선택지는 **탭 가능한 칩**으로 — 40-50대 사용자의 타이핑 부담을 줄입니다.

**(4) 숫자의 정직함 — 근거가 약하면 숫자를 만들지 않는다.**
- AI는 가격을 언급할 수 없습니다(환각 위험). 가격은 전부 서버가 크롤링 데이터로 계산합니다.
- AI가 지어낸 상품 id는 카탈로그 조인에서 걸러져 화면에 못 올라옵니다.
- 비교군 3건 미만이면 시세를 만들지 않고, 최고/최저 편차 4배 초과 그룹은 "시세 대비 N%" 대신 "12건 중 1번째로 저렴"이라는 반박 불가능한 사실만 보여줍니다.

**(5) 백엔드가 실질 로직을 가집니다.**
서버리스 함수가 OpenAI 중계만 하면 백엔드가 있을 이유가 없습니다. 속성 조인, 시세 분포, 절약 계산, 대화 정책 강제, 매칭 백스톱, 카탈로그 서빙이 전부 `api/`에 있고, `node api/_intel.js`·`node api/chat.js`로 실행되는 self-check가 순수 로직을 검증합니다.

**(6) UI — 데모가 아니라 운영 가능한 앱처럼.**
폰 프레임 안의 3탭 구조(AI 찾기 / 둘러보기 / 찜)가 전부 실제로 동작합니다. 둘러보기는 크롤링 473건을 브랜드·새상품/중고 필터로 탐색하고, 찜은 localStorage로 영속됩니다. 타깃(35-50 여성)에 맞춰 기본 17px·높은 대비·48px+ 터치 영역을 유지했습니다.

## 3. 겪은 어려움과 해결

**① 필웨이 크롤링 — 200 OK가 성공이 아니었다**

처음 타깃이던 중고명품 마켓 필웨이는 봇 차단 없이 200을 주고 상품 100건이 서버렌더링되어 있어 파싱까지 마쳤습니다. 그런데 8개 검색어로 96건을 모으니 중복 제거 후 12건. "디올 지갑"과 "구찌 가방"의 결과가 완전히 동일했고, 서버렌더링된 100건은 **전부 광고 슬롯**(남성 티셔츠 포함)이었습니다. 실제 결과는 클라이언트 렌더링이었던 겁니다.

> **배운 것**: 응답 코드와 그럴듯한 HTML은 크롤링 성공의 근거가 못 됩니다. **입력(검색어)을 바꿨을 때 출력이 실제로 달라지는지**까지 확인해야 검증이 끝납니다.

**② 크롤링 소스 확장 — 12곳을 실측해서 2곳이 남았다**

위 교훈을 기준 삼아, 파서를 쓰기 전에 curl로 먼저 실측했습니다.

| 소스 | 결과 |
|---|---|
| 필웨이 | 200이지만 전부 광고 슬롯 → 탈락 |
| 네이버쇼핑, eBay, SSG, G마켓 | 403 봇 차단 |
| 트렌비, 발란, 머스트잇, KREAM, 무신사, 29cm | SPA 빈 껍데기 / 4xx·5xx |
| **번개장터** | 공개 검색 엔드포인트, 쿼리 반응 확인 → **채택 (중고 매물)** |
| **다나와** | SSR HTML, 쿼리 반응 확인, 모델명+품번 → **채택 (새상품 가격비교)** |

다나와 채택은 우연이 아니라 발견이었습니다. 다나와 상품명은 품번까지 포함된 정식 모델명(`샤넬 블랙 19 라운드 미니 크로스백_AP0945`)이고, 상품 링크 자체가 판매처별 가격비교 페이지입니다. 덕분에 "중고 매물이 새상품 대비 얼마나 싼가"라는 이 제품의 핵심 기능이 실데이터로 성립했습니다 — 새상품+중고가 공존하는 모델 그룹 51개, 절약 계산이 붙는 중고 매물 155건.

**③ 실사용 테스트에서 잡은 결함 3개**

배포 전후로 실제 시나리오를 계속 태워보며 세 가지를 고쳤습니다.

1. **"샤넬 가방"에 7만원짜리 빈 상자가 매칭.** 제목이 `*클래식백* 샤넬 자석 박스 … 쇼핑백`이라 텍스트 매칭상 완벽한 후보였습니다. 부속품 필터를 넣되, `박스`를 통으로 막으면 "가방 + 박스"(진짜 가방)가, `참`을 막으면 `참월렛`(480만 원)이 죽어서 **합성어 단위로만** 차단했습니다.
2. **데님 복조리백(15만 원)에 "시세보다 92% 저렴" 배지.** 같은 그룹의 2.55 체인백(855만 원) 때문에 중앙값이 187만 원으로 잡힌 탓입니다. 편차 57배 집단의 중앙값은 시세가 아닙니다. 전수 조사 결과 편차 4배 초과 그룹은 전부 모델 미상 그룹이었고, 이 경계로 `medianReliable` 플래그를 만들어 **% 주장을 포기하고 순위·가격대만** 남겼습니다. 이 제품이 파는 게 "싸게 샀다는 확신"인데, 그 확신이 틀리면 기능이 없느니만 못합니다.
3. **실사용에서 "샤넬백"을 묻자 질문만 하다 빈손으로 끝남.** 초기 프롬프트 규칙("확신 없으면 되물어라")이 원인이었습니다. 규칙을 후보-우선으로 뒤집고, 질문 1회 제한을 코드로 강제하고, 키워드 백스톱을 추가했습니다. 같은 입력을 회귀 테스트로 박아 재발하지 않게 했습니다.

## 4. 아쉬운 점 · 개선 여지

**지금 구조의 한계**

- **매칭이 텍스트 기반이라 상품명에 없는 정보는 못 찾습니다.** "금색 D 장식", "물결 모양 뚜껑" 같은 묘사는 판매자가 안 쓰면 매칭에 반영되지 않습니다. → 상품 이미지를 Vision 모델로 캡셔닝해 색·형태·장식 속성을 카탈로그에 미리 생성해 두는 것이 1순위 개선입니다. 스펙에 없는 속성을 만들어 검색 가능하게 하는 것 — 카탈로그를 "저장"이 아니라 "생성" 시스템으로 보는 관점입니다.
- **카탈로그 473건 전체를 매 요청 프롬프트에 넣습니다.** 수천 건이 되면 토큰·정확도가 무너집니다. → 임베딩 벡터 검색으로 후보 20건을 좁힌 뒤 LLM에 넘기는 2단계 구조.
- **모델 그룹핑이 키워드 규칙이라 신규 라인을 못 잡고, 소스 간 동일 상품 판별이 거칩니다.** → 임베딩 클러스터링 + 품번 정규화.
- **시세가 크롤링 시점 스냅샷입니다.** → 주기 재수집(cron) + 가격 추이. "3개월 내 최저가" 신호가 구매 확신에는 더 강력합니다.
- **검수·정품 신호가 배지 하나입니다.** 시세보다 과하게 싼 매물은 오히려 위험 신호인데, 시세 분포를 이미 갖고 있으므로 "가격 이상치 경고"는 바로 붙일 수 있는 다음 기능입니다.

**검증하고 싶은 것 (과제 1의 실험 설계와 연결)**

- H1(서술형 검색이 발견율을 높이는가): 3턴 내 발견율, 대화 시작→카드 클릭률.
- H2(가격 확신이 결제를 앞당기는가): 절약 계산서 노출/미노출 A/B로 구매 링크 클릭률 비교. 특히 **%가 아닌 원화 절약액**이 더 강한 트리거인지 확인하고 싶습니다.
- 못 찾은 묘사는 그 자체가 "무엇을 원했는데 없었는가"라는 수요 데이터입니다 — 저장해서 소싱 우선순위로 쓸 수 있습니다.

**시간 배분 회고**: 초기 2시간 중 25분을 필웨이 실패 진단에 썼지만, 그때 세운 검증 기준("입력을 바꿔 출력이 달라지는가") 덕분에 2차 소스 확장에서는 12곳 실측을 10분 안에 끝냈습니다. 실패에서 재사용 가능한 기준을 뽑아내는 것이 실행 속도의 핵심이라는 걸 체감했습니다.
