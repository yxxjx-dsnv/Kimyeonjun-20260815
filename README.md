# 그거 있잖아

**정확한 상품명을 몰라도, 기억나는 대로 말하면 찾아주는 AI 쇼핑 메이트.**
찾아준 매물이 시세보다 싼지까지 알려줍니다.

🔗 **배포 링크: https://geugeo-itjana.vercel.app**

```
"디올 지갑인데 베이지 바탕에 남색 패턴이 깔려 있고, 카드 넣는 얇은 거였어"
                              ↓
   AI가 후보 3개 + 왜 이게 맞는지 근거 + 시세 대비 몇 % 저렴한지
```

## 로컬 실행

```bash
npm install
echo "OPENAI_API_KEY=sk-..." > .env.local

npm run crawl      # (선택) 매물 데이터 재수집 → data/products.json
vercel dev         # http://localhost:3000 — 프론트 + /api 함께 실행
```

`vercel dev` 없이 프론트만 볼 때는 `npm run dev` (5173 → 3000으로 `/api` 프록시).

## 구조

```
crawler/crawl.js   번개장터 중고 명품 매물 수집 → data/products.json + api/_catalog.js
api/chat.js        POST /api/chat — ChatGPT 상품 매칭 + 시세 계산 (Node 서버리스)
src/App.jsx        대화 UI + 상품 카드 + 가격 비교
data/products.json 크롤링 결과 (119건 / 50개 모델 그룹)
```

| 요구사항 | 구현 |
|---|---|
| 프론트엔드 React (JavaScript) | Vite + React 18, JSX |
| 백엔드 Node.js (JavaScript) | Vercel Serverless Function (`api/chat.js`) |
| 대화형 AI는 ChatGPT API | OpenAI `gpt-4o-mini`, JSON 모드 |
| 크롤링 데이터를 콘텐츠에 활용 | 크롤링한 119건이 ChatGPT 입력(카탈로그)이자 화면의 상품 카드 |
| 호스팅 | Vercel |

# 구현에 대한 설명

## 1. 무엇을 만들었나 — 과제 1과의 연결

과제 1에서 정의한 문제는 하나의 구매 여정에 이어진 두 가지입니다.

1. **탐색**: 명품의 상품명은 외국어 고유명사 조합(*디올 새들 로터스 월렛 오블리크*)인데, 사람 머릿속에 상품은 **이름이 아니라 특징의 묘사**로 저장된다. 키워드 검색창은 이 묘사를 받아주지 못한다.
2. **결정**: 고가 상품이라 "이 가격에 사도 되나"라는 확신이 없으면 결제를 미루고, 미뤄진 구매 의도는 대부분 돌아오지 않는다.

과제 1의 Core Loop 4단계를 그대로 구현했습니다.

| 과제 1 Core Loop | 구현 위치 |
|---|---|
| ① 서술형 입력 | `src/App.jsx` — 예시 문장 칩으로 "이렇게 말해도 된다"를 먼저 학습시킴 |
| ② AI 후보 제시 + 일치 근거 설명 | `api/chat.js` 시스템 프롬프트 규칙 2 |
| ③ 대화로 좁히기 | `followUpQuestion` — 색/크기/잠금장식/패턴 중 **한 번에 하나만** 되물음 |
| ④ 가격 확신 | `priceIntel()` — 같은 모델 매물의 최저/중앙/최고가와 시세 대비 할인율 |

## 2. 강조하고 싶은 설계 판단

**(1) 가격 계산을 프론트가 아니라 서버에 뒀습니다.**
서버리스 함수가 단순히 OpenAI를 중계만 하면 백엔드가 있을 이유가 없습니다. `api/chat.js`는 AI가 고른 상품 id를 카탈로그와 조인하고, 같은 `modelGroup` 매물들의 가격 분포를 계산해 붙입니다. 실질 로직이 백엔드에 있습니다.

**(2) AI에게 가격을 언급하지 못하게 막았습니다.** (시스템 프롬프트 규칙 6)
숫자는 LLM이 가장 잘 틀리는 영역인데, 여기서 틀린 숫자는 곧 "싸게 샀다"는 잘못된 확신입니다. AI는 **상품 매칭만** 하고, 가격은 크롤링 데이터로 서버가 계산합니다.

**(3) AI가 지어낸 상품은 화면에 못 올라옵니다.**
LLM이 목록에 없는 id를 반환할 수 있으므로, `byId.get()`으로 조인되지 않는 id는 조용히 버립니다. 실재하지 않는 매물 링크를 보여주는 것이 최악의 실패이기 때문입니다.

**(4) 데이터가 부족하거나 흩어져 있으면 "시세"라고 부르지 않습니다.**
이 제품이 파는 것은 "싸게 샀다는 확신"인데, 근거 없는 확신은 그 가치를 정반대로 뒤집습니다. 그래서 세 겹으로 막았습니다.

- 비교군 3건 미만 → 가격 정보를 아예 만들지 않음 (`MIN_PEERS`)
- 모델명 미특정 그룹 → "같은 모델" 대신 **"같은 브랜드·종류"**로 표기
- 최고/최저가 편차 4배 초과 → **`%` 주장을 포기**하고 순위와 가격대만 표시 (`MAX_SPREAD`)

마지막 조건은 실제 테스트에서 발견해 추가했습니다. 아래 '겪은 어려움' 참고. 결과적으로 비교군이 확보된 72건 중 35건만 "시세 대비 N%" 배지를 답니다.

**(5) 크롤링은 런타임이 아니라 1회성입니다.**
빌드 시점에 수집한 결과를 repo에 커밋해 씁니다. 의도적인 선택입니다.
- 사용자가 말을 걸 때마다 외부 사이트를 긁으면 **응답이 느려지고**, 상대 사이트 구조가 바뀌는 순간 서비스가 통째로 죽습니다.
- 상대 서버에 부하를 주지 않습니다.
- 이 MVP가 검증하려는 가설은 "서술형 검색이 통하는가"이지 "실시간 재고가 정확한가"가 아닙니다.

**(6) 타깃 사용자에 맞춘 UI.**
35–50세 여성이 주 사용자라 기본 글자 17px, 버튼 높이 52px, 높은 대비를 기준으로 잡았습니다. 빈 화면에 예시 문장 3개를 두어 "문장으로 말해도 된다"를 먼저 알려주는 것이 이 서비스에서 가장 중요한 온보딩이라고 봤습니다.

## 3. 겪은 어려움과 해결

**필웨이 크롤링 — 200 OK가 성공이 아니었던 문제 (가장 크게 시간을 쓴 곳)**

처음 타깃은 중고명품 마켓 필웨이였습니다. 검색 결과 페이지가 봇 차단 없이 200을 주고, HTML 안에 `goodsTitle`·`goodsPrice__current` 같은 깔끔한 클래스로 상품 100건이 서버렌더링되어 있어 파싱까지 마쳤습니다.

그런데 8개 검색어로 96건을 모았더니 **중복 제거 후 12건**만 남았습니다. 검색어를 "디올 지갑"에서 "구찌 가방"으로 바꿔도 결과가 완전히 동일했고, 확인해보니 서버렌더링된 100건이 **전부 광고 슬롯**(`goodsStatus = AD`)이었습니다. 심지어 명품이 아닌 남성 반팔 티셔츠였습니다. 실제 검색 결과는 클라이언트에서 별도로 렌더링되고 있었던 겁니다.

> **배운 것**: HTTP 200 + 그럴듯한 상품 HTML은 크롤링 성공의 근거가 못 됩니다. **검색어를 바꿨을 때 결과가 실제로 달라지는지**를 확인해야 검증이 끝납니다.

15분 룰을 적용해 필웨이를 버리고 대체 타깃 4곳(트렌비 / 발란 / 머스트잇 / 번개장터)을 동시에 실측했습니다. 트렌비는 SPA 껍데기(10KB)만, 머스트잇은 500, 발란은 연결 실패. **번개장터의 공개 검색 엔드포인트만 검색어가 실제로 반영된 실매물을 반환**해서 여기로 전환했습니다.

결과적으로 이 우회가 오히려 나은 선택이 됐습니다.
- 번개장터 상품명은 판매자가 직접 쓴 서술형이라(`"새상품급 정품 디올 오블리크 오거나이저 카드홀더 지갑 카드지갑 반지갑"`) 색상·종류·모델이 문장에 다 들어 있습니다. **묘사로 검색한다는 이 서비스의 컨셉에 정확히 맞는 데이터**였습니다.
- C2C 중고 마켓이라 같은 모델 매물이 여러 개 → **시세 분포가 실제로 나옵니다.** 119건 중 25개 모델 그룹이 2건 이상이라 가격 비교 기능이 실데이터로 동작합니다.
- `검수가능` 필드가 있어 과제 1에서 정의한 **'정품 불안'** 페인포인트를 그대로 배지로 연결할 수 있었습니다 (119건 중 112건).

**모델 단위 그룹핑 — 시세를 어떻게 정의할 것인가**

"시세 대비 N% 저렴"을 계산하려면 비교 대상이 같은 물건이어야 하는데, C2C 상품명은 형식이 제각각입니다. 임베딩으로 묶는 게 정석이지만 2시간 안에는 무리라, 상품명과 판매자 태그에서 모델 라인 키워드(오블리크, 마트라세, 모노그램…)와 종류(반지갑/장지갑/토트백…)를 규칙으로 뽑아 `브랜드|종류|모델`로 묶었습니다.

이 방식은 모델을 못 뽑으면 `샤넬|숄더백`처럼 넓게 묶입니다. 처음엔 라벨만 정직하게 바꾸면(모델 특정 그룹만 "같은 모델") 충분하다고 봤는데, 아래 테스트에서 그게 부족했다는 걸 확인했습니다.

**로컬 E2E 테스트에서 잡은 버그 2개**

배포 전에 실제 시나리오 5개(서술형 검색 / 모호한 입력 / 없는 브랜드 / 멀티턴 / 입력 방어)를 OpenAI 호출까지 태워봤고, 눈으로 봐야만 보이는 문제 두 개가 나왔습니다.

1. **"검정에 금색 체인 달린 샤넬 가방"에 70,000원짜리 빈 상자가 후보로 올라왔습니다.** 제목이 `*클래식백* 샤넬 자석 박스 … 쇼핑백`이라 텍스트 매칭상으로는 완벽한 후보였던 겁니다. 크롤러에 부속품 필터를 추가했는데, 여기서 한 번 더 걸렸습니다 — `박스`를 통으로 막으니 `"복조리 가방 + 박스"`(진짜 가방)가 죽고, `참`을 막으니 `참월렛`(charm wallet, 480만 원)이 죽었습니다. 그래서 `쇼핑백`·`자석박스`처럼 **합성어 단위로만** 차단하도록 고쳤습니다.

2. **데님 복조리백(15만 원)에 "시세보다 92% 저렴" 배지가 붙었습니다.** `샤넬|숄더백` 그룹 안에 2.55 체인백(855만 원)이 함께 묶여 중앙값이 187만 원으로 잡혔기 때문입니다. 편차가 **57배**인 집단의 중앙값은 시세가 아닙니다.

   데이터를 전수 조사해보니 편차 4배를 넘는 그룹은 **예외 없이 전부 모델 미상 그룹**이었습니다. 이 경계를 기준으로 `medianReliable` 플래그를 만들어, 편차가 큰 그룹에서는 `%` 주장을 포기하고 **"12건 중 1번째로 저렴 (15만~855만 원)"** 처럼 반박 불가능한 사실만 보여주도록 했습니다. 화면에도 "매물 차이가 커서 평균 시세를 계산하지 않았다"고 명시합니다.

   > 2번이 이 과제에서 가장 중요한 판단이었다고 생각합니다. 배지를 그대로 뒀다면 데모는 더 화려했을 겁니다. 하지만 이 제품이 파는 게 "싸게 샀다는 확신"인데 그 확신이 틀리면, 기능이 있는 것보다 없는 게 낫습니다.

## 4. 아쉬운 점 · 개선 여지

**지금 구조의 한계**

- **매칭이 텍스트 기반이라 상품명에 없는 정보는 못 찾습니다.** "금색 D 장식", "물결 모양 뚜껑" 같은 묘사는 판매자가 제목에 안 쓰면 매칭에 반영되지 않습니다. → 상품 이미지를 Vision 모델로 캡셔닝해 색상·형태·장식 속성을 뽑아두면 해결됩니다. 이게 1순위 개선입니다.
- **카탈로그 119건 전체를 매 요청 프롬프트에 넣습니다.** 지금은 동작하지만 상품이 수천 건이 되면 토큰·비용·정확도가 모두 무너집니다. → 임베딩 벡터 검색으로 후보를 20건쯤 좁힌 뒤 LLM에 넘기는 2단계 구조가 정답입니다.
- **모델 그룹핑이 키워드 규칙이라 신규 라인을 못 잡습니다.** → 임베딩 클러스터링으로 대체.
- **시세가 스냅샷입니다.** 크롤링 시점 가격이라 시간이 지나면 어긋납니다. → 주기적 재수집(cron) + 가격 추이 그래프. "3개월 내 최저가" 같은 신호가 구매 확신에는 훨씬 강력합니다.
- **판매처가 한 곳입니다.** 과제 1에서 정의한 "판매처별 가격 비교"는 지금 번개장터 매물 간 비교입니다. → 소스를 2~3곳으로 늘려야 진짜 크로스 플랫폼 비교가 됩니다.
- **대화 맥락이 매 요청 전량 전송입니다.** 길어지면 비용이 선형으로 늡니다. → 요약 압축 필요.

**제품으로서 더 해보고 싶은 것**

- **정품 판별 신호의 구조화**: 지금은 '검수 가능' 배지 하나입니다. 판매자 이력·가격 이상치(시세보다 과하게 싼 매물은 오히려 위험 신호)를 조합하면 "안심 지수"를 만들 수 있습니다. 시세 데이터를 이미 갖고 있어서 바로 붙일 수 있는 기능입니다.
- **찾기 실패의 자산화**: 못 찾았을 때 그 묘사를 저장해두면 "무엇을 원했는데 없었는가"라는 수요 데이터가 됩니다. 소싱 우선순위로 직결됩니다.
- **되묻기 전략 검증**: 지금은 "한 번에 하나만 묻기"로 고정했는데, 실제로 몇 턴 만에 원하는 상품에 도달하는지는 과제 1의 H1 실험으로 측정해야 할 부분입니다.

**시간 배분 회고**: 2시간 중 약 25분을 필웨이 크롤링과 그 실패 진단에 썼습니다. 처음부터 "검색어를 바꿔 결과가 달라지는지"를 검증 기준으로 잡았다면 5분이면 걸러냈을 문제였습니다. 크롤링 타깃은 파싱을 시작하기 전에 **응답이 입력에 반응하는지부터** 확인하는 게 맞습니다.
